# 语音输入法项目需求说明

## 项目定位

三天交付周期内，项目优先实现一个基于 Go 的“语音输入助手”MVP，而不是直接实现系统级输入法框架。该助手通过浏览器录音、本地 Go 服务处理、识别结果复制/展示的方式，完成语音输入法的核心链路，并为后续接入真实 ASR、全局快捷键、系统输入法协议预留接口。

## 目标用户

- 需要快速录入长文本的办公用户。
- 打字速度慢、但口述效率高的用户。
- 需要会议纪要、聊天回复、文档草稿等场景的用户。

## 核心需求

1. 录音输入：用户在页面按住录音按钮，说完松开。
2. 语音识别：Go 后端提供统一 ASR 接口，当前 MVP 使用 mock 实现，后续可接云端或本地模型。
3. 文本处理：支持清理语气词、自动标点、口令转换。
4. 结果输出：识别结果展示在文本框，并可复制到剪贴板。
5. 历史记录：保存最近 100 条识别结果，支持查看和清空。
6. 参数设置：支持开关自动标点、语气词清理、口令转换。

## 非功能需求

- 响应速度：短音频提交后后端应在 1 秒内返回 mock 结果；真实 ASR 接入后目标为 1-3 秒。
- 易用性：用户只需要打开本地页面，按住录音即可完成主流程。
- 成本控制：MVP 不依赖付费服务；真实 ASR 通过接口替换，便于比较本地模型和云 API 成本。
- 可扩展性：ASR、文本处理、历史存储、输入上屏拆分为独立模块。

## 三天计划

### 第一天

- 完成项目骨架。
- 完成 Web 控制台。
- 完成 mock ASR、文本处理、历史记录。
- 完成 README 和基础测试。

### 第二天

- 接入一个真实 ASR 方案，优先选择配置简单的云端 HTTP API 或本地命令行模型。
- 增加识别错误处理、超时处理和配置说明。
- 补充测试用例和演示数据。

### 第三天

- 优化 UI、补充演示流程。
- 整理 PR 记录、提交说明、依赖声明和原创功能说明。
- 录制或整理演示步骤，保证评委可复现。

## 暂不纳入 MVP 的需求

- Windows TSF 系统级输入法注册。
- macOS/Linux 原生输入法适配。
- 全局快捷键。
- 离线大模型内置分发。

这些能力会显著增加平台适配和调试成本，不适合三天内作为首要交付目标。
